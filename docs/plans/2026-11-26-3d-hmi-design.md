## 一、要解决什么

2D 操作层（`iot-unit-*` / `iot-faceplate-*`）解决"读数、诊断、操作"。它按 ISA-101 的显示
层级组织，灰阶、异常才上饱和色——**这是对的，不动它**。

2D 缺的是**空间**：一台设备在工艺流程的哪个位置、报警设备离主控室有多远、两个区域之间
怎么走。10 台设备时这是可有可无；到几十上百台、跨区域跨楼层时，"在哪"就是第一问题。

3D 空间层补的正是这一块，且**只补这一块**：

| 3D 空间层负责 | 3D 空间层不负责 |
|---|---|
| 空间定位（设备在哪、什么朝向） | 精确读数与趋势（→ 2D 的 L2/L3） |
| 状态表达（阀开/泵转/罐位） | 操作与写命令（→ 2D 的 faceplate） |
| 报警定位（哪台、什么级别） | 报警确认（→ 2D 报警抽屉） |
| 跨区域导航（点设备进 L2） | 工艺逻辑解释（→ 2D 单元画面） |

**判据**：如果一个 3D 需求可以由 2D 画面更好地承担，它就不该进 3D 层。

## 二、与 2D 的隔离（硬约束）

用户裁决是"分开、不混搭"，落到工程上是四条硬约束：

1. **3D 不是 2D 画布里的图元。** 不新增 `ah-3d-*` 类型的 maotu 图元——那会让 3D 场景被
   缩放、拖拽、嵌入到 2D 画面里，等于混搭。3D 是**独立文档 + 独立路由 + 独立渲染器**。
2. **独立路由**：`/view3d/:id`（运行）、`/edit3d/:id`（编辑，见 §七）。与 `/view/:id`、
   `/edit/:id` 平级，不互相嵌套。
3. **独立列表分区**：画面管理页分「2D 画面」与「3D 场景」两区（按文档 `$schema` 判别），
   各自独立打开入口。
4. **单一 WebGL 上下文**：整个 3D 视图**一个** canvas、**一个** renderer。
   这是硬性性能约束——Chrome 每页活跃 WebGL 上下文上限约 16 个（Chromium issue 40939743），
   而画面管理页会为每张可见卡片挂一个活的 `MtPreview`（`src/components/ScreenThumb.vue`）。
   3D 场景在列表页只出**静态海报图**，不挂 3D 渲染器。

> 为什么 3D 不能做成图元（补充理由）：即使不考虑规范，maotu 的 `vue` 型图元走
> `resolveDynamicComponent`（`maotu/dist/maotu.umd.js` 图元分派），每个 3D 图元实例会各
> 自创建一个 renderer——一张画面放两个 3D 图元就是两个上下文，编辑器与缩略图再乘一遍，
> 必然撞上下文上限。做成独立视图则全程只有一个。

## 三、视觉语言（3D 版的 ISA-101）

3D 没有现成标准可抄，本节是把 `hmi-style-guide.md` 的纪律翻译到三维的**设计定稿**。

### 3.1 基底

| 项 | 取值 | 理由 |
|---|---|---|
| 背景 | `#F0F0F0`（L1 同款浅灰） | 与操作层同一基底，不制造"另一个世界"的割裂感 |
| 设备常态色 | `#5B6570` 中性灰（同 2D 静态图元色） | 饱和色留给异常 |
| 着色 | **flat / matte**（`MeshLambertMaterial` 或 `MeshStandardMaterial` + `roughness=1, metalness=0`） | 禁照片级写实；写实贴图与数据争夺注意力 |
| 贴图 | 不使用（最多示意图解 decal） | 同上 |
| 光照 | 一盏方向光（"太阳"）+ 弱半球光 | 只为读出形体，不做戏剧性打光 |
| 阴影 | **默认关闭** | 阴影是最大性能开销，且增加视觉噪声；只在"结构感"确有必要时开 |
| 雾 | 远距离淡出（同背景色） | 深度线索，替代阴影的空间感 |
| 环境贴图 | 不使用 | 反射会引入非数据驱动的明暗，干扰状态判读 |

### 3.2 报警与状态编码

沿用 2D 的 ISA-18.2 三重冗余（颜色 + 形状 + 文字），在三维里的落地：

| 级别 | 颜色 | 形状标记 | 文字 |
|---|---|---|---|
| P1 | `#D32F2F` | 设备上方**三角**标牌 + 几何体红光环 | 浮层写 `P1` + 位号 |
| P2 | `#F57C00` | 六边形标牌 + 橙光环 | 浮层写 `P2` |
| P3 | `#FBC02D` | 方形标牌 + 黄光环 | 浮层写 `P3` |
| P4 | `#1976D2` | 圆形标牌 + 蓝光环 | 浮层写 `P4` |
| 正常 | `#5B6570` | 无标牌 | — |
| 停机/离线 | `#9E9E9E` | 无标牌，设备几何去饱和 | 浮层写状态词 |

- **只上色不改形**：设备本体几何形状不因报警改变（改变形体会让操作员失去空间记忆）；
  报警用**外挂**标牌与光环表达。
- **闪烁只表示"新到未确认"**，与 2D 同规则；确认后转常亮。
- **颜色不单独承载信息**：必须有形状 + 文字，照顾红绿色盲（约 8% 男性）。

### 3.3 状态驱动的几何（这是 3D 的真正价值）

设备几何随实时状态变化——与 2D 的 `ah-pump`（叶轮旋转）、`ah-tank`（液位）同一思路，但在三维：

| 设备类型 | 几何响应 | 驱动点 |
|---|---|---|
| 水泵 / 风机 | 叶轮旋转（转速正比于运行态，停止即停） | 运行状态位 |
| 阀门 | 阀杆/手轮转 90°（开/关） | 开关状态位 |
| 储罐 | 液位高度（缩放 Y） | 液位模拟量 |
| 电表 / 水表 | 表盘指针角度 + 数字轮 | 累积量模拟量 |
| 变送器 | 探头指示灯呼吸（仅异常时） | 状态位 |
| 管道 | 流向箭头沿管路平移（速度正比于流量） | 流量模拟量 |

**流向箭头是三维独有的表达**：2D 靠箭头符号，3D 里流动本身可读。这是最值得做的一处。

### 3.4 文字与读数

- **禁 3D 文字精灵**（sprite 贴图文字）：分辨率固定、不可选中、糊。
- **用屏幕空间 HTML 浮层**（`CSS2DRenderer`）：文字始终清晰、可选中、可交互。
- 浮层内容**克制**：位号（如 `WM-101`）+ 一个关键值 + 状态词。精确读数与趋势 → 点设备进 2D。
- **已知坑**（threejs 论坛）：`CSS2DRenderer` 的标签跟随有位置滞后；用射线做遮挡剔除
  （"标签被模型挡住就隐藏"）在模型复杂时非常慢。**对策**：不做逐帧射线遮挡测试，改用
  距离 + 优先级 + 屏幕空间重叠剔除。

## 四、数据模型

### 4.1 场景文档（3D scene doc）

独立于 2D 的 `IExportJson`，新 schema：

```jsonc
{
  "$schema": "agent-hmi.scene3d/1",
  "meta": {
    "name": "全厂 3D 空间总览",
    "group": "空间层",
    "unit_m": 1,                    // 1 场景单位 = 1 米
    "home": { "pos": [24, 18, 30], "target": [0, 2, 0] }  // 复位视角
  },
  "look": {                         // 视觉层参数（不写死，取自主题令牌）
    "bg": "#F0F0F0",
    "fog": { "near": 30, "far": 120, "color": "#F0F0F0" },
    "sun": { "dir": [1, 1.6, 0.8], "intensity": 1.15 },
    "hemi": { "sky": "#ffffff", "ground": "#9E9E9E", "intensity": 0.45 },
    "shadows": false
  },
  "nodes": [
    {
      "id": "wm1",
      "kind": "flowmeter",           // 几何原型（见 §六）
      "dev_id": "dev_wm1",           // 绑定的设备（可空：纯装饰构件）
      "pos": [-9, 0, 4],
      "rot": [0, 0.6, 0],
      "scale": 1,
      "tags": {                      // 点位绑定（通道 A，同 2D）
        "value": "flow_rate",
        "status": "status",
        "prio": "__prio"             // 合成报警优先级（lib/synthetic.ts）
      },
      "label": { "text": "WM-101", "show": "always" },
      "state": { "kind": "meter", "tag": "total_flow" }  // 几何响应规则
    }
  ],
  "links": [                         // 管线/连接（带流向）
    { "from": "wm1", "to": "wm2", "kind": "pipe", "radius": 0.12,
      "flow": { "tag": "flow_rate", "scale": 0.6 } }
  ]
}
```

### 4.2 存储：零 rs-iot 改动

rs-iot 的画面存储是**通用 JSON 文档 + 版本化**（lux `screen:*` 键族，`GET/PUT/DELETE
/api/v1/screens/{id}` + versions + rollback + 乐观锁）。3D 场景文档用 `$schema` 判别类型，
**存进同一键族**：

- rs-iot **不需要改一行代码**（存储层不解释文档内容）。
- hmi-studio 侧：`ScreenListView` 的卡片加载（`src/lib/screen-list.ts:loadScreenCards`）
  已经把每份 doc 都 GET 回来，按 `$schema` 分流到「2D 画面」/「3D 场景」两区即可。
- 版本化/回滚/乐观锁全部白拿——3D 场景的迭代也需要版本历史。

> 备选（不采用）：新增 rs-iot 资源 `/api/v1/scenes`。要多写路由 + 表 + 版本族，
> 收益仅是"物理隔离"。当前需求下 `$schema` 判别足够，且与 2D 共用版本语义更划算。
> 若将来 3D 场景的并发写入/权限需求与 2D 分化，再拆。

### 4.3 数据通路：完全复用

| 环节 | 复用 | 说明 |
|---|---|---|
| 订阅面 | `collectBinds(doc)`（`src/lib/binds.ts`） | 从场景文档收集 `nodes[].tags` + `links[].flow.tag`，生成订阅字段集 |
| 实时流 | `sse.ts`（既有 SSE 客户端） | 同 2D 运行页，rs-iot 侧零改动 |
| 写入 | 点值 → 场景节点状态 | 新增映射表 `field → node`；2D 是 `setDevicePointByID`，3D 是自己维护的节点状态机 |
| 报警 | 合成点位 `__prio` / `__area.<area>.prio` | 与 2D 同一套合成机制（`src/lib/synthetic.ts`），零新增 |
| 跳转 | `jump` + `?dev=` 机制 | 点 3D 设备 → 2D 的 `iot-faceplate-<type>?dev=dev_wm1` |

**结论：3D 层不需要任何新的后端数据通路。** 这是本方案成立的最大前提。

## 五、渲染架构

### 5.1 组件结构

```
src/views3d/
  Scene3DView.vue      # 路由页：装配 renderer/scene/相机/控制器/SSE/拾取/浮层
  scene-runtime.ts     # 纯逻辑层（可单测）：场景文档 → three 对象图；点值 → 状态
  geometry.ts          # 几何原型库（程序化建模，无外部资产）
  labels.ts            # CSS2D 浮层管理（去重、剔除、节流）
  picking.ts           # 射线拾取 → 设备 id
  theme.ts             # 3D 主题令牌（从 hmi-style-guide 派生）
```

`scene-runtime.ts` 与 three 对象图解耦：它只处理"文档 → 场景描述 → 应用点值"，渲染细节在
`Scene3DView.vue`。这样状态映射逻辑可以纯单测（不需 WebGL），对齐仓库既有做法
（`src/lib/synthetic.ts` 也是纯函数 + 单测）。

### 5.2 渲染预算

| 项 | 约束 | 依据 |
|---|---|---|
| WebGL 上下文 | **全程 1 个** | §二 约束 4 |
| draw call | 预算 100（10 台设备 + 管线场景） | 每可见 mesh 一次 draw call |
| 重复构件 | `InstancedMesh`（同型设备、管道支架、栏杆柱） | 官方示例：10 万实例 = 1 draw call |
| 三角形 | 设备原型 ≤ 2k 三角（低多边形平面着色） | 低多边形 + flat 着色，兼得风格与性能 |
| 帧率 | 1080p 目标 60fps（集显基线） | — |
| pixelRatio | 上限 2（`Math.min(devicePixelRatio, 2)`） | 高 DPI 屏填充率翻倍 |
| 阴影 | 默认关 | 阴影 pass 是最大开销 |
| 渲染策略 | **按需渲染**：相机移动 / 数据变化 / 动画进行中才 render | 静态画面占绝大多数时间，按需渲染直接省电 |
| 几何/材质 | 全局共享（同型设备共用 geometry + material） | 减少内存与状态切换 |

### 5.3 拾取

- `Raycaster` + NDC 坐标（相对 canvas 矩形，`getBoundingClientRect`）。
- **只对"可交互节点"做射线测试**（射线列表 = 设备节点集合，不是 `scene.children` 全体）。
- 设备节点用 `InstancedMesh` 时，射线返回 `instanceId` → 映射回设备 id。
- 拾取在 `pointerdown`（非 move）上做，避免拖拽相机时误触。
- 悬停高亮用 `pointermove` 但**节流**（≥100ms 一次）+ 只在未拖拽时执行。

## 六、几何原型库

**程序化建模，不用外部 glTF 资产**。理由：①与"禁照片级写实"一致；②状态可参数化
（液位高度、阀杆角度、指针角度天然是参数）；③零资产依赖、零加载等待、包体不膨胀；
④与 2D 的 `ah-*` 图元同一心智模型（参数化 SVG → 参数化 three 几何）。

原型清单（对应 iot-catalog 的 5 类设备 + 场景构件）：

| kind | 构成 | 状态响应 |
|---|---|---|
| `flowmeter` | 表体圆柱 + 表盘面 + 数字轮 | 数字轮转角 = 累积量 |
| `gasmeter` | 表体 + 余额窗 | 余额刻度 |
| `emeter` | 三相表箱 + 指示灯 | 指示灯 = 运行/故障 |
| `pump` | 泵壳 + 叶轮 | 叶轮旋转 |
| `valve` | 阀体 + 阀杆 + 手轮 | 阀杆转 90° |
| `tank` | 罐体 + 液位柱 | 液位缩放 Y |
| `pt` | 变送器探头 + 指示环 | 指示环 = 状态 |
| `pipe` | 圆柱段 + 法兰 + 流向箭头 | 箭头平移（流量） |
| `env` | 一体机立柱 + 探头 | 指示环 |

**每个原型同时产出两套几何**：`normal`（常态灰）与 `alarm`（饱和色）——用同一 geometry
不同 material 实例，避免每帧改色。

## 七、编辑（3D 组态器）

分两期，**先把运行视图做出来**：

**P1（先做）：场景文档生成器 + 运行视图**
- `src/screen-assets/iot-3d-layout.ts`：手写 iot-demo 厂区的空间布局（设备 x/y/z + 管线拓扑），
  与 `iot-catalog.ts` 的设备表一一对应。
- 场景文档由生成器产出（与 `iot-screens.ts` 同模式），`PUT` 进 rs-iot 的 `screen:*` 键族。
- 运行视图 `/view3d/:id` 完整可用。

**P2（后做）：浏览器内 3D 组态器**
- 复用 maotu 编辑器的交互范式但另起实现（不塞进 maotu 画布）。
- 能力：摆放设备原型（吸附到地面/对齐）、绑定 dev_id + tag、改朝向、改管线连接、
  设家视角、实时预览。
- 存盘：写回场景文档（同一个 PUT 接口 + 版本化）。

**P1 不做放置工具**是因为：布局是**一次性资产**（厂区不会天天挪设备），而放置工具是
**长期工具**（每次新增设备都要用）。先用生成器把资产做出来，验证 3D 层是否真的对操作员
有价值，再决定是否值得投工具。这与仓库既有做法一致（`iot-screens.ts` 也是生成器）。

## 八、风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| WebGL 上下文耗尽（列表页缩略图） | **高** | 3D 场景在列表页只出静态海报，不挂 renderer；运行视图全程 1 个上下文 |
| 编辑器/运行页反复挂载泄漏上下文 | **高** | `onBeforeUnmount` 强制 `renderer.dispose()` + `forceContextLoss()`；`MtEdit` 的 `:key` 重挂是既有机制，需实测重挂次数 |
| CSS2D 标签性能（滞后、遮挡剔除慢） | 中 | 不做逐帧射线遮挡；距离 + 优先级 + 屏幕空间重叠剔除；标签数上限（默认 ≤ 20 可见） |
| 3D 与 2D 视觉割裂 | 中 | 同底色（`#F0F0F0`）、同常态灰、同报警色表；3D 层只多"形体"这一维度 |
| 3D 层被误用于读数/操作 | 中 | 规范写死职责边界（§一表）+ 浮层只显示位号+1 值 |
| three.js 包体（core ≈ 150 KB gzip） | 低 | `import()` 动态加载，只在进入 3D 视图时拉取；不进 2D 首屏 |
| three.js 版本漂移 | 低 | 本地技能库已打 r187/r188 补丁；锁版本 + 迁移指南核对流程已建立 |
| 设备 3D 原型与真实设备形态不符 | 低 | 程序化原型是"符号化"而非"写实"，本就不追求与实物一致 |

## 十、验收判据

1. `/view3d/iot-plant-3d` 打开，10 台设备在场景中，位置与 `iot-3d-layout.ts` 一致。
2. 泵在运行时叶轮旋转、停机时停止；阀杆随开关状态转 90°；罐液位随模拟量变化。
3. 管道流向箭头速度随流量变化。
4. 某设备触发 P1 报警 → 该设备上方出现三角标牌 + 红光环 + 浮层写 `P1`；其余设备无饱和色。
5. 点设备 → 跳转到该设备的 2D faceplate（`?dev=`），返回后 3D 视角保持。
6. 报警清除后标牌与光环消失（与 2D 同源，同一条 `limit_alarm` 数据）。
7. 全程浏览器只有 1 个 WebGL 上下文（DevTools 确认）。
8. 列表页显示「3D 场景」分区，缩略图为静态海报，无 WebGL 上下文。
9. 1080p 下交互帧率 ≥ 55fps（`renderer.info.render.calls` ≤ 100）。
10. 2D 现有 16 张画面与全部 e2e **零回归**（3D 是独立路由与独立文档，不触碰 2D 通路）。

## 十二、开放问题

1. **3D 场景的编辑权**给谁？P1 阶段是"代码里写布局"，若现场要自己挪设备，P5 是必需的。
2. **厂区布局从哪来？** iot-demo 是虚构厂区，手写布局即可。真实项目里这来自 CAD/BIM
   导入（IFC → glTF），是另一个量级的工程，**不在本方案范围**。
3. **3D 层是否需要写命令？** 本方案明确不做（操作在 2D）。若将来要在 3D 里直接操作阀门，
   需另做安全设计（3D 拾错的代价远高于 2D）。
4. **多厂区/多楼层**是否需要？若要，场景文档要加 `levels` 概念与楼层切换 UI。
